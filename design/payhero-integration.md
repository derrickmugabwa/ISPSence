# PayHero integration

Implemented for the Kenya M-Pesa STK API (`/api/v2`). The global API is a
different contract and is not silently substituted. Provider-hosted sandbox
verification still requires the owner's account, endpoint and test credentials.

## Configuration and use

Open **Settings → PayHero** (fleet administrators only). Configure:

- Sandbox or live environment; collection is disabled initially.
- The provider-issued HTTPS API **origin**, without `/api/v2`.
- An active collection channel ID, and account ID if required for the account.
- API username/password generated by PayHero.
- The public HTTPS application origin, reachable by PayHero for callbacks.

`backend.payhero.co.ke` and `api.payhero.africa` are approved hosts. If PayHero
issues a different sandbox host, add that exact hostname to
`PAYHERO_ALLOWED_HOSTS` in the server environment and recreate the backend.
This variable is forwarded by `docker-compose.yml`; credentials are not stored
in that compose file. Origins cannot contain credentials, paths or query strings,
and provider redirects are rejected.

**Sandbox mode is not a payment emulator.** Use the endpoint, credentials and
test phone numbers issued for the sandbox. Choosing sandbox in the dashboard
does not turn production credentials into nonfinancial credentials.

Save settings and use **Test saved connection**. This reads payment channels;
it does not initiate payment. Blank credential fields retain saved credentials
only for the same environment and API origin. Switching either requires new
credentials. Settings use version checks. Credentials are encrypted at rest,
never returned to the browser, and included in the existing key-rotation sweep.
Configuration revisions are retained so pending attempts can still reconcile
against the credentials/channel they originally used.

### Bank channels

In **Settings → PayHero**, enter API credentials (or retain stored credentials
for the same origin and environment) and use **Load channels** to select an
active registered destination. **Add bank channel** opens a modal: load the bank
directory, select a bank, and enter your PayHero account ID, destination bank
account number and description. The backend obtains the Paybill number from
PayHero's `/api/v2/bank_paybills` directory and registers the destination through
`POST /api/v2/payment_channels`. Leading zeros in bank account numbers are kept.
You can create the first channel before saving collection settings.

Active channels fill the draft channel/account IDs; save settings separately to
use the destination. Inactive channels remain visible but cannot be selected.
Registration does not enable collections or request payment. Requests are
restricted to fleet admins, secrets stay out of responses/logs, and channel
lists follow bounded numeric pagination. A durable registration record prevents
duplicate POSTs after a timeout or concurrent submission; checking again first
looks for the matching registered destination. An unresolved registration needs
provider verification rather than automatic resubmission.

Provider contracts: [bank directory](https://docs.payhero.co.ke/docs/get-ph-bank-paybills),
[list channels](https://docs.payhero.co.ke/docs/get-payment-channels),
[register channel](https://docs.payhero.co.ke/docs/register-payment-channel).

Administrators open a payment record and explicitly request an M-Pesa payment.
Public package actions now open a real checkout at
`/portal/:slug/checkout/:packageId`; the independent simulated walkthrough
remains at `/portal-demo`, and draft template previews still have their own
simulation. An open checkout cannot silently change from sandbox to live when
settings change: the submitted environment must match the active configuration.

## Payment processing

1. Freeze package terms, allocate a payment record and reserve a distinct
   attempt in PostgreSQL before any outbound request. Public checkout creation
   uses a random request key, a hashed checkout capability, and an advisory lock
   to prevent duplicate customers/purchases on retries.
2. A worker claims queued attempts using database locks/leases and dispatches
   each attempt once. Whole-KES prices are converted from integer minor units:
   5,000 internal minor units becomes `amount: 50`. Fractional-KES prices are
   rejected rather than rounded because the Kenya STK request documents an
   integer amount. Kenyan mobile numbers are required.
3. Save PayHero's reference and checkout ID. Queued responses are pending, not
   paid. A timeout or crash after dispatch becomes **uncertain** and is never
   automatically resent. A scoped successful callback can recover a lost
   initiation reference through the documented receipt-code status lookup.
4. Store callbacks durably and acknowledge them before reconciliation. Their URL
   contains a separate random 256-bit secret for that attempt. Only its hash is
   used for inbound authentication; an encrypted copy supports initial dispatch.
   This is our callback capability, **not a claimed PayHero HMAC/signature**.
   The actual sandbox must preserve the supplied callback URL and Kenya payload.
5. Independently query PayHero using backend Basic authentication. Success needs
   the saved provider reference, M-Pesa outcome, matching receipt, callback
   amount, payer, external reference and checkout ID. Optional currency,
   amount, account and channel fields in the provider status reply must also
   match when present. A callback alone or a status boolean alone cannot fulfill
   a purchase. Missing/contradictory evidence stays pending or requires review.
6. A receipt ledger prevents reuse across attempts in the same environment.
   Verification, marking a live payment paid, preparing its live subscription
   and enqueuing the access job commit in one transaction. Customer locks
   serialize fulfillment. Repeated callbacks/status checks do not duplicate jobs.

Callbacks are capped at 16 KB and deduplicated. Their routes are mounted before
ordinary application URL/audit logging, and nginx suppresses access/error URL
logging for those secret-bearing paths. Redacted events and bounded callback
evidence are retained in dedicated tables. Treat callback URLs as secrets.

New collections are throttled by IP and by normalized payer phone, including a
60-second per-phone cooldown. Definitively failed attempts can be retried
explicitly with a new attempt. Pending, uncertain and review attempts cannot
start another charge for the same purchase. Unresolved results move to review
after 24 hours. Disabling/changing settings prevents previously queued requests
from being dispatched; already-sent attempts continue reconciliation.

## Sandbox, access and customer identity

Sandbox receipts and attempts are separate from live receipts. Sandbox success
does not mark a purchase paid, create a live subscription, issue credentials or
enqueue an access grant. The customer-facing status makes this explicit.

Verified live payments become **paid / awaiting activation**, with a live
subscription in **pending activation** and one access preparation job. Activation
and expiry timestamps remain null. Router/RADIUS provisioning still needs to
make access effective before any paid time starts. This integration does not
claim to make customers connected while that adapter remains unconnected.

Public checkouts create a provisional customer contact for the purchase. They
do not merge or renew an existing customer's account based only on an unverified
phone number. Returning-customer identity/device binding is separate work.
Checkout status requires an unguessable capability sent in a header; IDs alone
are insufficient. The browser retains its checkout identity in session storage
so a lost response/reload resumes the same payment rather than creating a new one.

Refunds/reversals are not automated. A conflicting callback after a successful
payment is retained as a review event and does not silently revoke access or
rewrite the verified payment. Operators must resolve such cases with PayHero.

## Routes

- Admin: `/api/billing/payhero/settings`, `/test`,
  `/payments/:id`, `/payments/:id/collect`, `/attempts/:id/recheck`.
- Public: `/api/public/payhero/availability`,
  `/portals/:slug/checkouts`, `/checkouts/:id`, `/checkouts/:id/retry`.
- Callback: `POST /api/payhero/callback/:attemptId/:secret`.

All management routes require a fleet administrator. Public projections exclude
API credentials, callback secrets and internal callback payloads.

## Validation

- 48 PayHero adapter/route tests passed: amounts, evidence matching, timeout
  behavior, HTTP Basic handling, permissions, private checkout status and callback
  boundaries.
- `scripts/check-payhero.cjs` runs service/database checks in a disposable schema
  using an injected fictional provider transport. It verifies credential
  encryption/masking, checkout replay, one dispatch, callback authentication and
  deduplication, sandbox isolation, one live access job without timestamps,
  uncertain-reference recovery, receipt/amount mismatch, environment changes,
  stale package rollback, disabling queued dispatch, and an explicit new attempt
  after definitive failure and the real per-phone retry cooldown. It never calls
  PayHero. Its disposable schema and temporary secrets were removed afterward.
- Frontend lint and production builds passed. Backend production builds passed.
- The actual checkout component was exercised in a loopback-only browser preview
  against `scripts/serve-payhero-ui-fixtures.cjs`. It showed the phone form,
  submission, asynchronous sandbox success and receipt, with no live-access claim
  or mobile horizontal overflow. These are fictional UI responses, not a
  provider-hosted sandbox test.
- Deployed HTTP checks passed for public availability (disabled), secret-free
  public responses, administrator authentication, capability-protected status,
  callback method handling and the 16 KB proxy body limit. Application baseline
  health and source-encoding checks passed.

Before using real payment rails, validate the issued sandbox's payloads,
callback delivery, status evidence and channel configuration. No credentials
were available during implementation; no real PayHero request or charge was sent.
