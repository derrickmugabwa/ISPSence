# AI assistant implementation

Scope: administrator assistant, Vercel AI SDK backend and AG-UI in V1. The web screen uses the AG-UI HttpAgent directly with dashboard-native controls. CopilotKit's selfManagedAgents integration was evaluated, but its installed release requires an enterprise license for production and reset the supplied message history during browser testing. It is not a production dependency. Initial tools are read-only and use existing application services. Backend authorization remains authoritative. MCP client/server, approved mutations and mobile follow later.

## First slice: Settings > AI

Fleet administrators can create up to twenty named provider connections, configure up to fifty exact model IDs per connection, enable/disable connections, select a default connection/model, and replace or remove credentials. Initial providers are DeepSeek, OpenAI and Google Gemini. All use fixed HTTPS origins; arbitrary provider endpoints are not accepted.

API keys use the existing AES-GCM encryption and key-rotation inventory. Responses disclose only whether credentials exist, never the secret or ciphertext. Blank credential input preserves the saved key; removal is explicit. Models and provider labels are validated. Default selection requires an enabled connection with credentials and a selected model. Disabling/removing credentials or removing the default model requires choosing another default first. Deleting the entire connection clears its default atomically.

Global configuration versions serialize edits and prevent stale saves. Connection tests use the saved credential revision, release database locks during HTTP I/O, and reject late results if credentials changed. Tests issue only bounded model-catalog requests with ten-second timeouts, fixed destinations and no redirects. They send no customer data, do not generate completions, and do not establish model tool-calling compatibility or sufficient billing balance. Gemini keys travel in a header, never a URL.

The UI uses the existing Settings navigation, modal dialogs and light/dark theme tokens. Server errors and audit events omit credentials and raw upstream bodies. The frontend also removes credential-bearing Axios request data from errors before caching them. Provider and model settings are server-side; no API key is persisted in browser storage.

Settings include enforced daily per-user request counts, output token limits, tool-step limits and conversation retention. New connections start with no provider selected and a generic name example. Provider selection is explicit; no provider is preferred or used as a fallback. The screen reports reserved requests and provider-reported token usage, without inventing spending figures.

## API and storage

- `GET /api/ai/settings`: public configuration fields, provider metadata and connection-check count.
- `POST /api/ai/settings/connections`, `PUT /api/ai/settings/connections/:id`: create/edit with global settings version.
- `DELETE /api/ai/settings/connections/:id`: remove saved connection/key with global settings version.
- `PUT /api/ai/settings/defaults`: default model and runtime policy defaults.
- `POST /api/ai/settings/connections/:id/test`: bounded catalog check with connection version; rate limited.

All routes require the existing authenticated fleet-administrator permission and send `Cache-Control: no-store`. Settings tables: `ai_connections`, singleton `ai_settings`, and redacted `ai_settings_events`. Migrations are additive and repeatable. Router permissions remain unchanged.

## Chat

`/assistant` provides a model picker for new conversations, personal conversation history, streamed Markdown, visible read-only checks, stop controls, deletion confirmation, inline errors and theme-aware styling. Raw HTML and remote images are disabled; rendered links must stay inside the application. AG-UI transport has no browser-defined tools or approval bypasses.

`/api/ai/chat` exposes options, conversation create/list/read/delete and the SSE `/run` endpoint. Chat requires a fleet-administrator session; API tokens and site-scoped accounts are refused. Ownership is checked for every history operation and run. Current permissions are rechecked before tools and before a successful run is committed. The server ignores supplied history, system prompts, tool definitions and forwarded context, accepting only the final bounded user text. It constructs model history from its own encrypted records.

Storage: `ai_conversations`, `ai_chat_runs`, `ai_chat_messages`, `ai_usage_days` and redacted `ai_tool_events`. Per-user serialization reserves daily requests atomically and permits at most two concurrent answers, one per conversation. Run IDs and user-message IDs prevent silent duplicate provider calls. Interrupted leases expire after 90 seconds; each HTTP run is bounded to 60 seconds. Model retries are disabled. Output tokens are divided across the configured maximum steps so the run cannot exceed the selected output allowance; reasoning-heavy models may need a higher allowance. Each run permits at most ten bounded tool calls.

Saved user/assistant text uses the existing encryption and key-rotation inventory. Only complete answers are saved. Failed, stopped and timed-out requests still count toward daily request limits; token totals include only returned provider usage and may undercount interrupted calls. Zero retention disables persisted text and cross-request model history, even though the current browser can still show its transient messages. An hourly cleanup applies the stricter of the conversation and current retention policy. Deleting a conversation removes its runs, messages and tool events; aggregate daily usage remains.

Tools cover customer lookup, requested/applied access and provisioning records, existing live billing dashboard aggregates, upcoming subscription expiry and last-reported router status. They exclude credentials, free-text notes, arbitrary SQL and router commands. Simulated sessions and unknown live telemetry are explicit; router reachability does not establish customer internet connectivity. These tools do not replace live hardware qualification.

## Router bandwidth tools

Added listRouterInterfaces and getInterfaceBandwidth, bringing the catalogue to 19 tools. Interface inventory uses selected Postgres fields, excluding credentials/configuration. A fixed Flux query safely quotes device/interface names and reads at most two recent samples per RX/TX field from interface_traffic. Rates are byte deltas times eight divided by actual elapsed seconds, not configured link speed or lifetime counter totals. Missing samples, reset counters, unsafe numeric counters, duplicate timestamps and gaps over 180 seconds yield unknown rates. Samples older than 180 seconds are explicitly historical. No fresh router probe is performed, and interface traffic is not attributed to billing customers or summed across overlapping LAN/bridge/WAN interfaces. Live customer accounting remains unavailable.

The tool instructions now explicitly distinguish available sampled router bandwidth from unavailable live per-customer session accounting. Consulted the official InfluxDB JS client documentation for bounded collectRows queries and safely quoted Flux literals.

## Consolidated catalogue policy

The current model-facing catalogue has 10 tools, superseding the earlier 19-tool rollout: listCustomers, getCustomerAccess, listCustomerSessions, getBillingSummary, listPayments, listPackages, listExpiringSubscriptions, listAccessAlerts, listProvisioningJobs and getRouterStatus. Nine overlapping names are no longer advertised or accepted as model tools. Shared internal readers preserve the prior datasets; only the consolidated entry points are registered. Canonical names govern audit events and each routed request consumes one call from the shared budget, with permissions rechecked before returning any result.

listCustomers supports search/list/filtered summary, so counts and pages use identical filters. getCustomerAccess selects overview, subscriptions, services, devices, schedule or structured history; getRouterStatus selects routers, interfaces or measured bandwidth. Conditional inputs reject missing targets and inapplicable filters. These sections are requested independently rather than dumping the entire customer/router record.

listCustomerSessions supports customer or fleet scope, list/summary, status, service type, paired Nairobi dates and recent/download/upload/total-usage ordering. Its totals use full stored counters for sessions STARTED in the date window; they are not exact calendar-window traffic or instantaneous speed. Asking for live mode returns unavailable/null and never silently substitutes simulation.

Before adding another model tool, extend the relevant existing dataset tool with a coherent filter, view or bounded detail projection. A new tool requires a distinct dataset or operation that cannot fit an existing tool cleanly; document that reason and add coverage/permission tests. Do not expose arbitrary query/SQL tools. Preserve independent payment records versus financial aggregates, catalogue data, fleet expiry actions, alerts and provisioning datasets as focused tools.
